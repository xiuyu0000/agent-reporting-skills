## 1. 文档约定

本文是需求与约束说明书，不是实现设计。本文定义 Skill **必须表现成什么样**，不规定其代码组织、页面 DOM、CSS 数值、脚本名称、模板替换方式或持久化技术。

本文使用以下规范词：

- **必须 / 不得**：发布和验收不可违反的要求。
- **应 / 不应**：默认要求；只有存在明确、可解释的例外时才能偏离。
- **可以**：允许但不强制的行为。

本文已于 2026-08-12 获用户确认，是该次破坏性升级的产品需求事实源。此后任何需求条款变更都必须先做影响审计，再同步 [design.md](design.md) 与 [task.md](task.md)，不得只改其中一份。确认记录见 §18。

## 2. 产品摘要

`deliver-dual-audience-report` 保留现有公开名称，但从“生成 Agent Markdown 与静态人类叙事 HTML”升级为“生成 Agent Markdown 与自足的交互式审批 HTML”。

升级后的 Skill 服务于一个明确场景：单个知识工作者需要审批 Agent 产出的方案。Skill 必须把方案重组为少量可独立裁决的决策块，区分哪些内容需要用户拍板、哪些只需知会、哪些属于常规直行，并让用户在阅读原处完成表态。全部决定必须自动形成可供下一轮 Agent 直接消费的结构化回执。

默认交付物仍然面向两个受众，但人类产物的职责发生变化：

- Agent Markdown 面向后续 Agent，负责精确续作。
- 审批 HTML 面向单个人类审批者，负责理解、判断和反馈。

独立的人类叙事 HTML 不再是默认产物。

## 3. 为什么要做

### 3.1 被替换的流程

旧流程要求用户阅读静态人类报告；阅读中出现意见时，用户需要切换到笔记工具记录，再返回原文重新定位。读完后，还要手工整理零散笔记并组织成下一轮提示。

### 3.2 核心问题

Skill 必须同时解决三个问题：

1. **注意力稀释**：多数只需知道或可直接执行的信息，与少数需要判断的信息同权重呈现。
2. **工作记忆过载**：阅读反应没有在原处落盘，只能暂存在工作记忆中。
3. **反馈闭环断裂**：记录意见需要切换应用，且零散意见不能直接驱动下一轮 Agent。

只在静态文档上增加自由批注不能完整解决这些问题。目标体验必须同时改变内容组织、判断交互和反馈输出。

## 4. 用户与系统角色

### 4.1 主要用户

主要用户是需要独立审批 Agent 方案的单个知识工作者。用户可以不是开发者，且不应被要求理解数据模型、自动化框架或实现技术。

### 4.2 系统角色

- **生成方 Agent**：核实事实、组织 Agent Markdown、切分和分诊决策块、生成审批 HTML。
- **审批者**：阅读方案、逐块表态、记录随手记并导出回执。
- **消费方 Agent**：验证并消费回执，生成修订版、定稿版或派生的新方案。

同一个 Agent 可以先后承担生成方和消费方角色，但两个阶段必须遵守各自的输入输出约束。

## 5. 适用范围与触发边界

### 5.1 必须触发

同时满足以下条件时，Skill 必须适用：

- 用户明确要求审批、评审、批准或逐项反馈 Agent 方案，或者已接受的计划明确承诺审批版交付；
- 内容可以拆成至少 4 个可独立裁决的事项；
- 主要审批者是一个人；
- 任务需要同时保留 Agent 续作上下文和人类审批界面。

典型场景包括执行方案、重要变更方案、研究后形成的决策方案、需要逐项批准的项目计划和后续修订轮次。

### 5.2 不得触发

以下情况不得使用本 Skill 强行生成审批工作台：

- 多人共同或并行审阅同一文档；
- 少于 4 个决策块的一次性小方案；
- 没有审批目标的自由探索式阅读；
- 只要求单一静态 Markdown 或 HTML 报告；
- 只要求聊天内回答；
- 只要求代码修改，且没有独立的方案审批交付物。

不适用时，Agent 应采用更轻量或更成熟的对应方式，不得为了触发 Skill 人为扩充决策块数量。

### 5.3 公开触发入口

Skill 的公开触发描述和默认提示必须同步表达以下合同：

- 任务是单人审批；
- 存在明确审批目标；
- 初始内容至少包含 4 个可独立裁决事项；
- 默认产物是 Agent Markdown 与自足审批 HTML。

这些公开入口不得继续把 Skill 描述为静态 Agent 报告与静态人类叙事报告的生成器，也不得让单一报告、自由阅读或纯代码任务误触发。

## 6. 产品目标与成功标准

### 6.1 产品目标

Skill 必须达到以下结果：

- 用户无需离开审批页面即可记录决定和想法。
- 用户的注意力优先投入真正需要裁决的事项。
- 常规内容可以低成本处理，但重要事项不能被批量通过掩盖。
- 审批结果可以直接供下一轮 Agent 消费，无需用户再次手工整理。
- Agent Markdown 与审批 HTML 共享同一事实基础，不出现结论、约束或版本漂移。
- 审批中断、复制失败或受限运行环境不得导致已经记录的内容无恢复路径。

### 6.2 功能验收标准

在宣称功能完成前，必须证明：

- 两个默认交付物均真实存在、内容完整、相互一致且可在最终交付中同时访问；
- 审批者可以完成分诊浏览、四种动作、随手记、T0/T1 整批通过和回执导出；
- `review-packet/1` 可以驱动修订、暂缓回答、派生主题、冻结通过块和全通过定稿；
- 部分审批、冻结重新打开、旧动作迁移、恢复能力降级和非法输入拒绝均符合本文；
- 至少一个完整的“方案 → 审批 → 回执 → 修订或定稿”合成场景通过验证。

### 6.3 真实使用标准

在宣称真实场景有效前，必须至少完成一份真实业务方案的闭环，并收集用户负担反馈。

累计完成 3–5 份真实方案后，应验证：

- T0/T1 块平均裁决时间少于 10 秒；
- 一份方案的主动审阅时间不超过 30 分钟；
- 从初版到定稿的返工轮次不超过 2 轮；
- 用户主观判断新流程的认知负担低于旧的“阅读—切换记录—手工汇总”流程。

测量时必须记录所用口径与样本数。样本不足时只能报告“尚未验证”，不得将目标写成已达成事实。

## 7. 默认交付契约

### 7.1 Agent Markdown

Agent Markdown 必须让一个没有隐藏对话上下文的后续 Agent 能够继续工作。它至少应包含：

- 目标、范围、排除项、语言和事实截止时间；
- 权威来源及冲突处理顺序；
- 当前状态、关键事实、决定、约束、风险、阻塞和开放问题；
- 决策块及其稳定标识、分诊、依赖、冻结和变更状态；
- 下一步动作和已完成的验证；
- 明确说明该文档是综合说明，不是新的事实源。

### 7.2 审批 HTML

审批 HTML 必须同时满足“可判断”和“可操作”：

- 离线打开即可使用，不依赖外部运行时服务或网络资源；
- 判断所需的解释、对比、数据、流程和必要术语在同一文件内可见或可原地展开；
- 悬停提示只能补充说明，不能承载判断所必需的信息；
- 外部链接只能作为延伸阅读，不能成为完成判断的前置条件；
- 复杂关系应在确有帮助时使用内嵌、可访问的可视化，不要求每个复杂块强制配图；
- 保持文档阅读形态，决策块按方案叙事顺序呈现，不按分诊层级重排；
- 支持完整审阅、部分审阅、中断续审和冻结块重新打开。

### 7.3 事实一致性

两个默认交付物必须来自同一份经过核实的事实集合，并在以下内容上保持一致：

- 标题、语言、事实截止时间和方案版本；
- 核心事实、决定、约束和重要不确定性；
- 决策块的稳定标识及其当前状态；
- 哪些内容已批准、待修改、存疑、派生或冻结。

允许两个产物使用不同顺序、详略和措辞，但不得形成语义冲突。任何自动校验都不能替代最终的人工语义一致性检查。

### 7.4 交付完成条件

初始方案或后续修订版只有在以下条件全部满足时才算交付完成：

- Agent Markdown 与审批 HTML 均存在并通过相应验证；
- 两者没有未替换占位符、无效内部链接或已知事实冲突；
- 两个产物都位于用户确认的输出边界内，且没有静默覆盖既有文件；发生文件名冲突时必须停止并请求明确处置或使用经确认的新名称；
- 最终回复同时提供两个真实产物的链接；
- 交付说明标明事实截止时间和剩余不确定性。

## 8. 逻辑输入模型

本节定义公共语义，不规定具体编程语言或文件内嵌方式。

### 8.1 共享事实集合

生成方必须先记录：

- 标题、语言、事实截止时间、输出位置及其公开或私有边界；
- 按可信度排序的来源层级；
- 需要在两个产物中保持一致的事实、决定、约束、风险和开放问题；
- 每条核心事实或决定的稳定标识、置信度和来源引用。

如果来源冲突足以改变结论，生成方必须停止并暴露冲突，不得静默选择。

### 8.2 审批文档

每份审批文档必须具备：

- 稳定文档标识；
- 标题；
- 内容版本；
- 日期或事实截止时间；
- 正整数审批轮次；
- 一句话摘要；
- 按叙事顺序排列的决策块；
- 可选的页内术语表。

“内容版本”“审批轮次”“回执协议版本”和“状态协议版本”是四个不同概念，不得混用。

### 8.3 决策块

每个决策块必须代表一个可以被独立裁决的事项，而不是任意自然段。每块必须具备：

- 在同一方案全部轮次中稳定且唯一的块标识；
- 分诊层级 `T2`、`T1` 或 `T0`；
- 不超过 16 个中文字符或等价长度的短标题；
- 不超过 40 个中文字符或等价长度的一句话摘要；
- 足以完成判断的正文；
- 可选的依赖块标识列表；
- 适用时的冻结轮次和本轮变更说明。

修订块和新增块必须说明本轮发生了什么变化。此前已通过且本轮未触及的块必须保留原文并标记冻结轮次。

### 8.4 分诊规则

分诊必须按后果和判断需求进行：

| 层级 | 进入条件 | 呈现与审批要求 |
|---|---|---|
| `T2` 决策 | 不可逆、承诺显著资源、对外可见、偏离先例、Agent 置信度不足，或触及用户明确利害中的任一条件 | 默认展开；必须写明“为什么需要用户拍板”和“希望用户回答什么”；必须逐块显式表态 |
| `T1` 知会 | 用户需要知道背景、理由或风险，但不需要作选择 | 默认以一句话摘要为主，可按需展开，可进入整批通过 |
| `T0` 直行 | 常规、有可靠先例且可回滚 | 视觉弱化但仍可展开，可进入整批通过 |

用户必须能对任何层级使用任何动作。用户对 T0/T1 提出修改或存疑时，下一轮分诊应吸收这一反馈，不得以原层级拒绝意见。

### 8.5 规模硬约束

一个审批轮次必须同时满足：

- 当轮审批文档展示的全部决策块不超过 15 个，包括冻结块；
- 当轮审批文档中的全部 T2 块不超过 7 个，包括冻结块。

生成方必须在交付前验证上限，超限文档不得直接交付。只有在内容能够拆成多份分别满足 4–15 块、T2 不超过 7 块、可独立理解且依赖闭合的审批文档时，才允许拆分；每份拆分文档必须拥有独立的文档身份、自己的双产物和自己的审批修订轮次，任一块的全部依赖都必须位于同一份拆分文档内。生成方必须告知用户拆分边界。无法满足这些条件时必须报告阻塞。不得用同一方案的修订轮次表达初始内容分批，也不得只显示警告后继续交付超限审批版。

### 8.6 结构有效性

以下任一情况都会使审批文档无效：

- 文档标识、版本或轮次缺失；
- 块标识缺失或重复；
- 未知分诊层级；
- T2 缺少裁决原因或具体提问；
- 依赖指向不存在的块、自身或形成循环；
- 冻结块的正文相对其批准版本发生未授权变化；
- 超过规模硬约束。

无效文档不得作为可审批交付物发布。

## 9. 审批行为契约

### 9.1 决策状态

每个活动块初始为“待处理”。活动块一次只能有一个当前动作。对同一块重新选择动作时，后一次决定覆盖前一次决定；用户也必须能够撤销决定，使其回到“待处理”。

冻结块不是活动块，默认不可直接施加动作，也不进入进度、批量操作或待处理导航。用户必须显式“重新打开”冻结块，才能使其重新成为活动块并表态。

### 9.2 四种动作与随手记

| 动作 | 用户含义 | 输入要求 | 对源块的含义 |
|---|---|---|---|
| `PASS` 通过 | 没有意见，批准本块 | 无需补充文字 | 本轮通过；消费回执后按本次批准轮次冻结。只有全部传递依赖都具备执行资格时，本块才具备执行资格 |
| `EDIT` 修改 | 方向或细节需要改变，包含精简、删除和扩展 | 必须填写可执行的修改意见；可以附原文引用 | 下一轮只修改本块，标记本轮变化并重新开放审批 |
| `TOPIC` 新主题 | 从本块派生一个值得独立立项的事项 | 必须填写主题标题；补充说明可选 | 派生独立方案；不批准源块，也不得修改源块。源块下一轮保持活动状态 |
| `HOLD` 存疑 | 当前信息不足，暂时不能决定 | 必须填写需要先回答的问题 | 禁止执行；下一轮携带回答并重新分诊、重新开放审批 |
| 随手记 | 记录想法但不形成决定 | 自由文本 | 不改变块状态，不授权修改或执行 |

每个 `TOPIC` 决定必须与且只与一个新主题条目对应。统计按决定计算一次，不得因同时存在决定记录和主题清单而重复计数。

用户也可以记录与具体块无关的全局新主题。全局主题没有来源块，不构成块级 `TOPIC` 决定，也不进入块级进度或动作统计。每个全局主题必须具有可稳定识别的条目，并在回执消费时与且只与一份独立方案对应；成功派生前它是未消费诉求，成功派生并记录消费后不再阻止原方案定稿。

### 9.3 引用与意见管理

- 用户在触发动作时选中了块内文本，系统应把该文本作为意见引用保存。
- 引用必须保留来源块关系，并限制为足以定位语境的长度。
- 过滤必须至少覆盖“全部”“待处理”“仅 T2”和“已批注”。
- 决策清单必须支持按块号、意见文字和主题检索。
- 已记录的决定、随手记和新主题必须可以修改或删除。
- 删除决定后，块必须恢复为待处理；删除随手记不得改变块状态。
- 删除或替换块级 `TOPIC` 决定时，与其一一对应的主题条目必须同步删除或替换；全局主题可独立管理。

### 9.4 整批通过

整批通过只能作用于当前仍待处理的 T0/T1 活动块，并必须经过页面内的第二次确认。

T2、冻结块、已有非 PASS 决定的块和不在当前作用域内的块不得被整批通过影响。确认前必须显示将被处理的块数量；处理后必须清楚说明 T2 未受影响。

### 9.5 进度与完整性

进度的分母是本轮全部活动块，冻结块不计入。分子是已经具有当前动作的活动块；随手记不构成决定，不计入分子。

- 所有活动块均有决定时，本轮是“完整审批”。
- 仍有活动块待处理时，本轮是“部分审批”。
- 回执导出始终可用，不得强迫用户先完成全部块。

部分审批中未表态的块必须保持原状并继续处于活动状态，不得被解释为默认通过、默认存疑或放弃。

冻结块被重新打开但尚未获得新决定时，历史批准记录必须保留，但当前执行资格必须暂停。部分回执必须明确携带该重新打开状态；只有包含新决定的有效回执才能替代历史批准状态。

### 9.6 键盘与低成本交互

所有核心审批能力必须可以仅用键盘完成。默认快捷键语义为：

- `j` / `k`：移动到下一个 / 上一个块；
- `n`：跳到下一个待处理块；
- `1`–`4`：依次触发通过、修改、新主题、存疑；
- `Esc`：取消当前编辑或关闭当前临时界面；
- `Cmd/Ctrl+Enter`：保存当前意见或笔记。

触发任一标记动作不得超过两次点击或一次按键；需要文字说明的动作可以在触发后要求输入内容。完成有效决定后，应自动移动到下一个待处理块，但不得使用户失去返回和改判能力。

## 10. 审批回执与状态接口

### 10.1 Markdown 回执

Markdown 回执必须可直接粘贴给下一轮 Agent，至少包含：

- 文档标识、标题、内容版本、审批轮次、审阅时间和进度；
- 是否为部分审批；
- 给下一轮 Agent 的明确处理规则；
- 按动作分组的块标识、标题、引用和用户意见；
- 新主题、随手记、冻结沿用块、已重新打开块和总评；
- 四种动作的统计。

### 10.2 JSON 回执

机器可读回执的协议标识必须是 `review-packet/1`。其公共语义至少包括：

- 被审文档的稳定标识、标题、内容版本和轮次；
- ISO 8601 审阅时间；
- 已决定数、活动块总数和部分审批状态；
- 冻结沿用块；
- 本轮已重新打开的冻结块；
- 决定、随手记、新主题、总评和统计。

每条决定必须引用一个现存块，并使用受支持动作。JSON 回执与同次导出的 Markdown 回执必须表达相同决定。

“冻结沿用块”“已重新打开块”和“具有新决定的块”必须能被无歧义地区分。已重新打开但未表态的块必须列入重新打开集合且不列入冻结沿用集合；具有新决定的重新打开块同时出现在重新打开集合与决定明细中。三者与当前文档冻结状态不一致时，回执无效。

动作与通用批注语义的对应关系为：

| 本契约动作 | 通用语义 |
|---|---|
| `PASS` | 评价并批准 |
| `EDIT` | 编辑请求 |
| `TOPIC` | 关联或派生 |
| `HOLD` | 提问 |
| 随手记 | 评论 |

### 10.3 状态文件

中断续审状态的协议标识必须是 `review-state/1`。状态必须绑定文档标识、内容版本和审批轮次，并足以恢复：

- 当前决定及其意见和引用；
- 随手记；
- 新主题；
- 总评；
- 被重新打开的冻结块。

状态文件不是审批回执，不得被消费方当作执行或修订授权。

### 10.4 历史动作迁移

导入历史审批状态或回执时，必须继续接受 `TRIM` 和 `EXPAND`：

- 两者都迁移为 `EDIT`；
- 原动作语义必须以前缀或等价的可见方式保留在意见中；
- 迁移不得静默丢失原意见；
- 新导出的状态和回执不得再生成 `TRIM` 或 `EXPAND`。

历史兼容必须具备原子性。在文档标识、内容版本和审批轮次通过验证，旧动作完成规范化，进度与统计按规范化后的明细完成重算，且全部结构校验成功前，不得对当前状态产生任何可观察修改。任一步失败都必须保持原状态不变；成功导入后不得残留旧动作计数。

缺少内容版本或审批轮次等充分身份的旧状态不得自动恢复。只有用户明确确认其来源文档、内容版本和轮次后，迁移流程才能补全身份并继续；无法建立唯一身份时必须失败关闭。未知的其他旧动作或未来协议版本不得猜测迁移。

### 10.5 旧报告合同

`dual-audience-report-contract-v1` 是旧静态报告接口，不是新版审批接口。

- 新版不得把它静默解释为审批文档、审批回执或审批状态。
- 输入旧合同且未经过显式迁移时，必须报告接口不兼容，并且不得生成看似有效的审批交付物。
- 旧合同对应的静态人类叙事 HTML 不再是新版默认输出。

## 11. 回执消费与轮次协议

### 11.1 消费前验证

消费方必须先完成适用的历史动作规范化，再验证回执协议、文档标识、内容版本、审批轮次、块引用、动作、依赖、主题映射、冻结沿用、重新打开、进度和统计一致性。汇总字段不得覆盖或纠正与其冲突的明细；两者不一致时必须判定回执无效。

回执与当前活动方案不匹配、已经消费过、格式损坏或引用无效时，消费方必须失败关闭：不修改方案、不执行事项、不派生主题，并给出可定位的错误。

同一份有效回执被重复提交时，消费结果必须幂等，不得重复派生方案或重复执行同一动作。

### 11.2 动作消费

- `PASS`：按本次批准轮次冻结源块，包括重新打开后再次通过的块。只有其整个传递依赖闭包均具备执行资格时，本块才能标记为具备执行资格。
- `EDIT`：只修改该决定引用的源块；下一轮必须给出变化说明并重新开放该块。
- `HOLD`：不得执行源块；下一轮必须先回答问题，并将答案与重新分诊后的块一起提交审批。
- `TOPIC`：生成一个独立、可审批的新方案；源块原文不得因此改变，也不得因此获得执行资格。
- 全局新主题：每个条目幂等地派生一份独立、可审批的新方案；成功后记录为已消费，不改变任何源块。派生失败时必须保持未消费，不得据此完成原方案定稿。
- 随手记：只作为上下文参考。若其中包含能力或内容诉求，消费方可以将其转成下一轮新增决策块，但不得静默执行。
- 总评：作为全局修订指导，但不得覆盖具体块决定或未触及块保护规则。

“具备执行资格”只表示审批和依赖条件已满足，不构成对外部系统、文件、人员或生产环境的自动执行授权。实际执行仍必须遵守当前任务的权限、审批和安全边界。

任一上游依赖处于待处理、重新打开未决定、`EDIT`、`HOLD` 或 `TOPIC` 时，所有直接和间接依赖它的下游块都不得具备执行资格。下游块可以保留既有正文和历史批准记录，但必须暂停执行资格；上游恢复资格后，受其语义变化影响的下游块仍须显式重新打开并重新批准，不得自动恢复执行资格。

### 11.3 未触及块保护

修订版不得修改回执没有触及的块。此前已通过且未触及的块必须原文冻结；待处理但未表态的块必须原样保持活动。

### 11.4 下一轮

消费有效回执后，修订输出的审批轮次必须递增一次：

- 被修改、存疑、以 `TOPIC` 派生主题或重新打开后尚未重新通过的块是活动、待处理块；
- 重新打开后获得新 `PASS` 的块按当前批准轮次重新冻结；
- 新增块必须标明本轮变化；
- 已通过且未重新打开的块是冻结块；
- 冻结块不进入新一轮进度分母。

### 11.5 全通过定稿

仅在以下条件同时满足时，消费方才能生成全冻结定稿态：

- 所有活动块均为 `PASS`；
- 不存在 `EDIT`、`HOLD` 或 `TOPIC`；
- 不存在块级 `TOPIC`，且所有全局新主题均已成功派生并记录为已消费；
- 随手记或总评中不存在要求改变方案或新增能力的诉求。

生成定稿态时不得改写任何块正文；必须移除仅用于本轮修订的变化标记，并为所有块保留批准轮次。后续修改冻结内容的唯一行为入口是“重新打开 → 新决定 → 新回执”。

本契约只定义逻辑轮次与冻结行为，不规定方案文件应放在哪个目录，也不要求索引、归档文件夹或特定文档治理系统。

## 12. 恢复与降级行为

### 12.1 自动恢复

审批环境具备可靠的本地持久化能力时，系统必须按文档标识、内容版本和审批轮次隔离保存状态，并在重新打开时提示用户恢复了何时、多少项记录。用户必须可以清空恢复状态并重新开始。

本文不规定具体持久化技术。

### 12.2 持久化不可用

环境不支持自动持久化或保存失败时：

- 页面必须明确告知用户当前进度不会自动保存；
- 页面必须提示用户离开前导出状态；
- 手动导出和导入 `review-state/1` 的能力必须继续可用；
- 持久化失败不得使已经加载的审批内容不可读或阻止回执导出。

运行中发生保存失败时，提示必须在自动持久化不可用期间持续可见，不得只显示会自动消失的一次性提示。用户成功导出后，只有当前状态与最近一次成功导出的状态完全一致时，才可以将提示降级为“当前状态已手动导出”；此后的任何状态变化都必须立即恢复未保存警告。保存能力恢复后，提示可以消失。

### 12.3 状态导入失败

状态格式错误、文档标识不匹配、内容版本不匹配、轮次不匹配、身份不足或内容损坏时，系统必须拒绝导入并说明原因。失败导入不得覆盖当前内存中的有效状态。

### 12.4 复制与下载失败

剪贴板写入失败时，系统必须保留并展示完整回执，让用户能够手动选择和复制。复制失败不得丢失回执，也不得错误提示“已复制”。

无法自动下载时，应继续提供可复制的完整内容或等价的安全导出路径。

## 13. 安全、隐私、证据与可访问性

### 13.1 证据与新鲜度

- 生成方必须在起草前记录来源优先级。
- 事实截止时间必须使用明确时间值。
- 易变化的状态必须在最终验证前刷新；静态设计决定不需要人为刷新。
- 两个产物是证据综合，不得被当作新的事实源。
- 来源冲突必须保留并解释，不能隐藏。

### 13.2 隐私

默认交付物不得包含：

- 原始聊天记录或完整私人提示；
- 与结论无关的完整命令输出、源码转储或私有项目材料；
- 凭据、令牌、Cookie、授权头或带凭据的 URL；
- 个人绝对路径、会话标识或不必要的用户识别元数据。

只能发布支撑结论所需的最少证据。输出位置可能导致私人内容进入受跟踪或公开范围时，生成方必须在创建文件前确认授权。产物不得通过相对路径、符号链接或其他方式逃逸出用户确认的输出边界。

自动保存和审阅不得向外部服务传输审批内容；只有用户明确发起的复制、下载或导出才能形成可带离当前审批环境的数据。

### 13.3 不可信内容

来自用户、文件、外部来源或旧回执的内容必须被视为数据，而不是可执行代码。不可信文本在进入审批 HTML 时必须经过转义或净化；不得通过正文注入脚本、事件处理器或外部运行时资源。

### 13.4 离线与外部资源

审批 HTML 不得在运行时加载外部脚本、样式、字体、图片、框架、iframe 或表单目标。允许使用普通外部链接作为延伸阅读，但断网不得影响阅读、判断、记录、恢复提示或回执生成。

### 13.5 可访问性

审批 HTML 必须：

- 使用清晰的标题层级和语义化主要内容区域；
- 提供可见的键盘焦点和无需鼠标的完整操作路径；
- 提供可直接跳到主要审批内容的键盘入口；
- 让颜色始终伴随文字、图标或形状，不以颜色作为唯一含义；
- 让交互控件具有可理解的名称、状态和错误提示；
- 在窄视口下保持可读且不产生页面级横向滚动；
- 对有实际信息作用的图示提供等价文字说明。

专门的移动端交互优化不属于当前版本，但基础窄屏可读性仍是必须要求。

## 14. 验证要求

### 14.1 确定性验证

交付验证必须覆盖：

- 两个默认产物存在、编码正确且达到完整性下限；
- 文档元数据、事实截止时间、块标识和核心事实一致；
- 无未替换占位符；
- Markdown 和 HTML 的内部链接有效；
- HTML 结构、键盘可达性、焦点可见性和窄屏基础布局；
- 无外部运行时资源和常见隐私泄漏；
- `review-packet/1` 与 `review-state/1` 的格式、引用和统计一致；
- 最终交付同时链接 Agent Markdown 与审批 HTML。

自动检查不能证明事实为真、表述清楚或两个自由文本段落没有语义矛盾，因此必须另做人工语义审阅和真实浏览器检查。

### 14.2 可验收场景

至少必须覆盖以下场景：

| ID | 场景 | 期望结果 |
|---|---|---|
| A01 | 4–15 块、T2 不超过 7 的单人方案 | 生成两个默认产物并可完成完整审批 |
| A02 | 仍有待处理块时导出 | 生成明确标记为部分审批的 MD/JSON 回执，未表态块保持活动 |
| A03 | 整批通过包含 T0/T1 与 T2 | 只处理待处理的 T0/T1，T2 保持不变 |
| A04 | EDIT 后消费回执 | 只修改被触及块，标记变化并在下一轮重新开放 |
| A05 | HOLD 后消费回执 | 不执行源块，下一轮携带回答并重新分诊 |
| A06 | TOPIC 后消费回执 | 派生一个独立方案，不批准或修改源块，不重复统计；源块下一轮回到活动、待处理状态 |
| A07 | 所有活动块通过，且没有未消费的全局新主题 | 生成不改正文的全冻结定稿态 |
| A08 | 重新打开冻结块 | 该块重新进入活动集和进度分母，可重新表态 |
| A09 | 导入 `TRIM` / `EXPAND` | 迁移为带原语义的 `EDIT`，新输出不再产生旧动作 |
| A10 | 自动持久化不可用 | 显示明确降级提示，手动状态导入导出仍可用 |
| A11 | 剪贴板失败 | 保留完整回执供手动复制，不误报成功 |
| A12 | 重复块、坏依赖、未知动作或文档/版本/轮次不匹配 | 失败关闭，不修改现有状态，并指出错误位置 |
| A13 | 当轮文档共 16 块或共 8 个 T2 | 仅在各拆分文档均满足 4–15/7、身份独立且依赖闭合时拆分并各自生成双产物，否则报告阻塞；不交付仅带警告的超限工作台 |
| A14 | 多人协作、少于 4 块或自由阅读 | Skill 不触发，不人为扩块 |
| A15 | 两个产物核心事实或版本冲突 | 验证失败，不宣称交付完成 |
| A16 | `C` 被 HOLD，`B` 依赖 `C`，`A` 依赖 `B`，而 `A/B` 已 PASS | `A/B` 保留批准记录但均不具备执行资格；依赖变化后须显式重新审批受影响下游 |
| A17 | 冻结块重新打开后，分别测试未表态与再次 PASS | 未表态时保留历史批准但暂停资格并进入部分回执；再次 PASS 后按当前轮次重新冻结 |
| A18 | 状态只缺内容版本，或同文档同轮次但版本不同 | 不自动恢复；只有明确建立旧状态身份后才可迁移，否则原子拒绝 |
| A19 | 不可信正文、状态或回执包含脚本、事件处理器或危险 URL | 作为惰性内容安全呈现或被拒绝，不执行注入内容 |
| A20 | 仅使用键盘完成重新打开、动作覆盖/撤销、TOPIC 成对删改、状态导入导出及复制失败后的手动复制 | 全流程可完成，焦点顺序和状态反馈可感知 |
| A21 | 所有活动块通过，同时存在一个全局新主题 | 全局主题只派生一份独立方案并记录消费；派生成功后原方案可定稿，失败时原方案不得定稿 |
| A22 | 自动保存失败后手动导出，随后继续修改 | 状态与导出快照一致时显示已手动导出；后续修改立即恢复未保存警告 |

## 15. 迁移与兼容边界

### 15.1 保留

- 公开 Skill 名称 `deliver-dual-audience-report`；
- Agent Markdown 作为精确续作产物；
- 一个共享事实集合驱动两个受众产物；
- 来源优先级、事实新鲜度、隐私最小化和交付前验证；
- 最终回复必须同时链接两个真实产物；
- 内容无关的可选使用记录可以继续存在，但记录失败不得使已经验证的交付失效。

可选使用记录不得包含对话或提示正文、路径或文件名、项目名、命令、输出、会话标识、凭据或任一交付物内容。记录失败必须保持非阻断，也不得伪造成功记录。

### 15.2 破坏性变化

- 人类默认产物从静态叙事 HTML 变为自足的交互式审批 HTML；
- 触发条件从“任何明确双报告任务”收窄为“有审批目标且适合逐块裁决的单人方案”；
- 旧 `dual-audience-report-contract-v1` 不再是新版有效合同；
- 初始化、验证和触发用例必须围绕决策块、审批回执和轮次闭环重新定义；
- 不再允许用一份静态人类报告满足第二个交付物。

用户明确指定文件名、语言或安全输出位置时，应继续优先采用用户指令，只要这些指令不破坏本契约的两个产物、隐私和审批行为要求。

## 16. 明确非目标

当前版本不包含：

- 多人实时或异步协作审批；
- 少于 4 块内容的工作台化；
- 无审批目标的叙事阅读替代；
- 默认独立人类叙事版；
- Info_ORG、`00_索引.md`、固定目录、归档布局或其他项目专用文档治理；
- 块级手动改层控件；
- 跨轮次可视化差异比较；
- 深色模式；
- 专门的移动端产品形态；
- Todoist 或其他任务工具的一键导入；
- 多文档审批队列；
- Agent 预填用户决定；
- 自动执行任何已批准事项；审批结果只能形成下游可评估的执行资格，不能扩张任务权限。

这些能力只能在真实使用数据支持后另行立项，不得作为当前版本已承诺能力。
